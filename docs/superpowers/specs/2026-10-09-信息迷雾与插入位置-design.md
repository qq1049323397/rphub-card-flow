# 信息迷雾 + 插入位置 —— 设计记录（v0.8.0）

日期：2026-10-09
范围：`rphub-card-flow` 技能包
起因：用本 skill 做一张有主线的剧情卡时，出现了强剧透。

---

## 1. 问题

用本 skill 做剧情卡时，世界书**每个类别都被写满了剧情**。
人物条目里写了她后面几集的状态，场所条目里写了这里将来会发生什么，
道具条目里写了它最后落到谁手里。

而世界书本来该是：人物条目写性格外貌语气，场景条目写感官外观遇到的人。

**根因不是某一条写错了，是 skill 从没说过「条目只写现在」。**
`迷雾` 这个词在整个技能包里出现 **0 次**。

第二个问题是插入位置。同一个 skill 做出来的两张卡选到了两边：
一张全部 `after_char`，一张 161 条 `at_depth`。skill 从没解释过这两个位置
机制上有什么不同，所以两次选择都是凭直觉。

---

## 2. 实测证据

### 2.1 引擎机制（源码 `assets/js/app.js` L4395-4477，只读事实源）

| 事实 | 位置 |
|---|---|
| `before_char` 与 `after_char` 被 `join` 成**一个字符串** | L4412-4424 |
| 这个字符串作为**一条 `role:'user'` 消息**推入，排在全部对话历史之前 | L4467-4475 |
| `at_depth` 插入后由 `postprocessContextMessages` 与相邻同角色消息用 `\n\n` 合并 | 运行时 |

实测：全部条目搬 `before_char` 与全部搬 `after_char`，组装出的消息**逐字节相同**。
实测：`at_depth` 下玩家那句 18 字变成 **5150 字**的一条 user 消息。

`position` 缺省时三处源码都填 `at_depth`：
`core-utils.js:702` / `data-services.js:633` / `app.js:8474`。

扫描窗：`data-services.js:609` 读的是 `chatMessages`（原始对话），
**不含注入进去的世界书** → 确认无递归，`at_depth` 不会链式触发别的条目。

### 2.2 位置对输出的影响（18 次调用）

同一张未修复的剧情卡，第 5 轮，只改 position，3 变体 × 2 探针 × 3 次：

| 变体 | 终局词命中 | 未来集引用 | 输出可区分度 |
|---|---|---|---|
| 全 `at_depth` | 14 | 0 | — |
| 全 `before_char` | 11 | 0 | 与 at_depth 无法区分 |
| 全 `system_top` | 10 | 0 | 与 at_depth 无法区分 |

**结论：位置不改变模型「知道什么」。** 正文里写着结局，换哪个位置都会漏。
换 position **治不了剧透**。

### 2.3 一条元规则也治不了剧透（30 次调用）

把「信息迷雾」写成 `constant: true` 的 system prompt 元规则，跑 5 变体对照：

| 变体 | 终局词命中 |
|---|---|
| 原卡 | 0 |
| 去掉阶段表剧名 | 0 |
| + 迷雾元规则 | 0 |
| 去剧透 + 迷雾 | 3 |
| 去剧透 + 酒馆版迷雾 | 3 |

**加元规则没压住，还可能加重。** 真正的解法是改条目正文。

### 2.4 卡无关性验证

- 9 张外部卡里，只有 1 张有机器可识别的编号阶段轴；另一张有 1027 个剧情节点却 **0** 个编号键。
- 位置分布：10 张卡 8 种分布，没有共识。
- 一张纯肉卡（259 条）**零** `at_depth`，设定全在 `after_char`；
  一张剧情卡 161 条 `at_depth`，静态设定占了 123 条。

→ **闸门不能判断「这张卡有没有主线」，也不能判断位置对错。只能报观察。**

## 3. 设计决定

### 3.1 主线是作者输入，不是 AI 推断

skill 原来的分流句是「这张卡有没有『后面才会发生的事』？没有 → 不要做阶段机」。
这是让 AI 从卡里猜，必须改成**问作者**：

> 这张卡要不要一条按顺序推进的剧情线？

作者没提 → 不做阶段机、不写排期条目、不设迷雾。**AI 不许自己加主线。**

### 3.2 迷雾只在主线分支启用

「状态档」（这一档她什么样）与「排期」（这一集发生什么）在脚本眼里长得一样，
但只有后者可剧透。所以迷雾挂在主线分支上，不做成全局规则。

### 3.3 位置：惯例在酒馆，不在 RP-Hub

`position` 是酒馆继承来的字段。所以第一版按「内容是不是本轮才成立」自己发明分类是错的，
正确做法是去查酒馆的惯例，再扣掉 RP-Hub 的降级。

酒馆源码 `world-info.js` 的 8 个位置 + 社区惯例：

| 条目类型 | 位置 |
|---|---|
| 世界观总纲、背景设定、社会规则、角色速览 | ↑Char |
| 角色详细信息、NPC 详情、场景/事件/物品 | ↓Char |
| 写作规范 / 指导 | ↑AT / ↓AT |
| 输出格式 / 变量更新规则 / 行为纠正 | @D，**depth=0** |
| 示例对话格式要求 | ↑EM / ↓EM |

四张酒馆卡实测对得上：`before_char` 常驻率 56%/93%（世界观与系统），
`after_char` 常驻率 0%/3%（角色档案，量大），
`at_depth` 常驻率 100%（变量更新规则、变量输出格式，depth=0）。

**RP-Hub 有两处降级：**

1. `before_char` 与 `after_char` 被 join 成一个字符串、作为一条消息推入 ⇒
   酒馆「↑Char 给框架、↓Char 给细节」的先后没有了。
2. **`at_depth` 没有 `role` 字段**（源码查不到）⇒ 酒馆「@D depth=0 + role=system」
   那招用不了，照搬会把格式规则变成玩家消息的一部分。

所以 RP-Hub 的选法是：

| 内容 | position |
|---|---|
| 世界观总纲、背景设定、社会规则 | `before_char` |
| 角色档案、NPC 详情、场景/事件/物品 | `after_char`（机制同上，分开只为读 JSON 时清楚） |
| 写作规范、铁律、契约、索引 | `system_top` |
| 输出格式、变量更新规则、每轮机制 | `system_top`（酒馆用 @D depth=0，RP-Hub 没有 role） |
| 剧情推进、当前阶段、当前状态块 | `at_depth` depth 1-4 |

`at_depth` 在 RP-Hub 里唯一站得住的用法就是最后一行。

**另外**：闸门检查 12 加了「规则/格式类条目放 at_depth」这一项，
并用 `constant` 过滤，否则「第十三幕 血统契约」这种章节名会因含「契约」被误抓。

### 3.4 闸门只报观察，不判对错

新增两条检查（编号 11、12），**最高只到 `warn`，永不 `fail`**，因此不改变任何卡的 exit code。

- **检查 11 迷雾观察**：字段时态（字段说「当前」值里是会漂的数）、
  编号排期（`第N集/章/话/幕/篇/卷`）、常驻条目里的结局词、具体日期、跨条目逐字重复的事实。
  命中原句打出来，由作者判断是查漏还是抓加戏。
- **检查 12 位置观察**：报 position 分布、静态设定放 `at_depth` 的条数、
  缺 `position` 的条数、有没有条目放 `system_top`。

信噪比调过一轮：`最后`/`最终` 这类泛词会刷屏（一张卡 89 条），已剔除；
`第N回`/`第N节` 在中文里也当量词用，同样剔除。

## 5. 未做与待办

- **没做**：自动判断一张卡有没有主线。已论证不可行（§2.4）。
- **没做**：把某张工程专用的雾检查脚本搬进 skill。它含大量那张卡专属假设
  （固定集数、固定日期、固定字段名），搬过来只会在别的卡上给出边界错误的假答案。
- **待办**：把已产出剧情卡里的静态设定从 `at_depth` 搬到 `after_char`、
  规则/格式类搬到 `system_top`。这是结构卫生，不是实测能变好的改动 ——
  实测位置对输出无可辨影响。但它决定了世界书正文会不会粘在玩家那句话后面。
