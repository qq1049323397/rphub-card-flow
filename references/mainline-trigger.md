# 主线 / 阶段：怎么搭才真的能触发

> 来源：2026-09-30 用户报「纯用 skill 做出来的主线剧情是关键词，根本没办法触发」，
> 对 4 张成品卡（大世界 / 小卡 / 纯日常）逐条对照源码链定位。
> 结论：不是键写错了，是**整台机器没搭**。
> 运行时证据见 `key-reachability.md`；键本身怎么设计见 `keyword-design.md`。

## 〇、先分流：这张卡到底要不要主线

**大多数卡不需要。** 纯肉卡、单场景卡、日常陪聊卡，看完这行就可以关掉本页。

判据只有一句：

> **这张卡有没有"后面才会发生的事"？**

- 没有 → **不要做阶段机**。硬加一个阶段行只会白烧上下文，还会让 AI 每轮分心。
- 有（有幕、有章、有真相分期揭开、结局会变） → 往下读。

**不要**因为"别的卡有"就给自己的卡加。**不要**因为"看起来专业"就加。

## 一、原理：一条令牌的往返

主线触发**不是**计数器，**不是**"玩家待够多少轮就自动进下一幕"。
它是一条令牌的往返，四个环节缺一不可：

```text
① 常驻规矩（世界书里一条 constant 条目）
      ↓ 每轮进 prompt，要求 AI 在正文写一行当前阶段
② AI 写出那一行（例：[ARC_MAIN|主线1|可以留在这里吗]）
      ↓ 这行文字被存进聊天记录
③ 下一轮，它落进关键词扫描窗
      ↓ 宿主拿它去匹配所有条目的 keys
④ 挂这个阶段名的章节条目被拉进 prompt
```

**断在哪里，就"根本不触发"在哪里。**

| 断点 | 症状 | 谁负责 |
|---|---|---|
| ① 没有常驻规矩 | AI 压根不知道要写阶段行 | 产出者条目 |
| ② 规矩写了但 AI 不照做 | 阶段行时有时无 | 写法与位置 |
| ③ 阶段行被宿主**文风过滤**改写 | 存储里就已变形，键必然失配 | 阶段名避开过滤词表（见 §六附） |
| ④ 章节条目的键与阶段行**不逐字相同** | 永远匹配不上 | 键名对齐 |

> **卡内正则不会吃掉阶段行。** 这一条曾被写反，值得单独说清：
> 卡里的美化/隐藏正则**只作用于渲染那一份**，从不写回 `chatHistory`
> （`applyDisplayRegex` → `processRegex({isDisplay:true})` 的返回值只喂给画面）。
> 扫描窗读的是存储里的原文（`app.js` L4359 起，该函数体内 `processRegex` 出现 **0 次**）。
> 所以 ArC 那条 `ARCADIA主线阶段隐藏`（`markdownOnly: true` / `replaceString: "$1"`）
> **玩家看不见阶段行，但下一轮照样扫得到** —— `markdownOnly` 的正则
> 在 prompt 路径上会被 `if (isPrompt && userOnly) return;` 直接跳过。
> **"美化里不显示"和"触发不了"是两件事。**

最常见的死法是 **①**：只写了章节条目、挂了键，但**全卡没有任何一处告诉 AI
"你要每一轮写一行阶段"**。于是那些键就是 `ST_A1` 这类没人会写出来的暗号，
条目永远躺在那儿。

## 二、三件套（缺一不可）

### 件 1 · 产出者：一条常驻条目

这是**唯一的契约来源**，必须 `constant: true`。
它要一次说清五件事，**不能省任何一件**：

1. **阶段行的逐字格式**（分隔符、字段顺序、包裹符）
2. **全部阶段的完整枚举**（从头到尾列全，让 AI 知道有几个、叫什么）
3. **初始阶段是哪一个**
4. **推进规则**（见第四节：靠收尾事实，不靠轮数）
5. **这一行放在回复的哪个位置**（且**每轮都要保留**，不是只写一次）

真实范文（ArC，436 字，`constant: true` / `order: 120` / `position: before_char`）：

```text
正式剧情回复在人物名单之后单独保留一行主线阶段；独处场景将它放在正文之后。
阶段标记采用以下准确形式：
[ARC_MAIN|序章0|综漫的日常]
[ARC_MAIN|主线1|可以留在这里吗]
[ARC_MAIN|主线2|天亮以前]
[ARC_MAIN|主线3|回家的路]
[ARC_MAIN|主线4|黑之枢机]
[ARC_MAIN|主线5|白之枢机]

初始阶段为序章0·综漫的日常。各阶段沿自身入口、正在发生的事与收尾事实推进；
阶段收尾发生的同一轮，采用已经进入的下一阶段名称。……
每轮保留一条与当前事实对应的阶段行，放在引导选项之前。
名称与编号逐字使用上面的形式。……
```

**这段话里有四句是承重墙，少一句就断**：

| 句子 | 少了会怎样 |
|---|---|
| 「阶段标记采用以下准确形式」+ 完整枚举 | AI 自己发明格式，键对不上 |
| 「初始阶段为序章0·综漫的日常」 | 开场没有起点，第一轮就无从写起 |
| 「……收尾事实推进」 | AI 不知道什么时候该换（或按轮数乱换） |
| 「**每轮**保留一条……逐字使用上面的形式」 | 只写一次，第二轮起令牌消失 |

### 件 2 · 每轮那行：格式要"人能写、机能认"

格式自己定，但必须满足三条：

- **逐字固定**：分隔符、字段数、顺序都不能变。AI 稍微改写就匹配不上。
- **AI 能在正文里自然写出**：别设计成人根本不会打的字符串。
- **与正文用词不冲突**：包裹符越独特越好，避免和普通句子混淆。

对比：

```text
✅ 人写得出、机器认得准
   [ARC_MAIN|主线1|可以留在这里吗]

❌ 暗号，AI 不会主动写
   ST_A1

❌ 太像普通句子，没法稳定匹配
   现在是第一阶段
```

**为什么 `ST_A1` 不行**：它是给程序看的编号，不是叙事语言的一部分。
世界书里可以列它，但 AI 写正文时不会把这五个字符敲出来 —— 除非你**明确要求**
它逐字输出（project8 的 `状态块` 就做了这件事），否则键永远扫不到。

### 件 3 · 消费者：每个阶段各成一条，键 = 那一行逐字

- **一条阶段 → 一条条目**（小卡 1~2 条，大卡每章一条）
- `constant: false`（它们要靠阶段行拉进来，不能常驻，否则全剧透）
- 键 = 阶段行的**逐字**内容，用正则包住

ArC 的实际挂法（6 条消费者）：

```text
comment: 主线·序章0·综漫的日常
keys:    ["\\[ARC_MAIN\\|序章0\\|综漫的日常\\]","\\[IDENTITY_INJECTION\\]"]
constant: false   order: 1090000   position: at_depth   depth: 2   scanDepth: 2

comment: 主线·主线1·可以留在这里吗
keys:    ["\\[ARC_MAIN\\|主线1\\|可以留在这里吗\\]"]
constant: false   order: 1090000   position: at_depth   depth: 2   scanDepth: 2
```

注意 `[` `|` `]` 在正则里都是元字符，**必须转义**。手写容易漏，
用 `node regex-doctor.mjs <卡>` 过一遍。

## 三、键名对齐：交付前必须逐个核

**两条独立命名 = 键白设。**

| 病灶 | 例子 | 后果 |
|---|---|---|
| 契约写 A，键写 B | 契约输出「第二阶段」，条目键是「第二次博弈」 | 永不匹配 |
| 契约写全名，键写简称 | 契约 `[ARC_MAIN\|主线1\|可以留在这里吗]`，键只写 `主线1` | 部分匹配不到 |
| 枚举少列一个 | 契约列 5 个阶段，实际有 6 个 | 第 6 阶段永远没有条目 |

**核法**：把产出者条目里的枚举逐行抄出来，一条一条去对章节条目的 keys。
**逐字比对，不看意思。** 差一个标点就算不对。

## 四、推进靠收尾事实，不靠轮数

这是最贵的一个语义错误。

```text
✅ 这一阶段的收尾事实已经发生 → 下一轮起采用下一阶段名称
❌ 超过 30 轮 → 自动进入下一阶段
```

**为什么**：玩家闲逛十轮，主线剧情并没有推进。
按轮数推进的卡，玩起来是"剧情自己往前走，玩家跟不上"。

ArC 的原话：「主线不会因玩家空闲而自动播放」——
它的推进完全由**当轮叙事收尾**决定。

数值门槛可以存在，但只用于**该用数值的地方**（角色亲密度、战斗撤退判定等），
**不要**拿它当主线阶段的开关。

写推进规则时，给**每一个**阶段写清：

- **入口**：什么局面算进入这一阶段
- **正在发生的事**：这一阶段里世界在动什么
- **收尾事实**：什么事件发生算这一阶段结束

## 五、小卡到大卡：同一套契约，只改条目数量

**结构完全一样，规模不同。** 不要因为卡小就省掉契约。

| | 小卡（1~3 阶段） | 中卡（4~6 阶段） | 大卡（7~15+ 阶段） |
|---|---|---|---|
| 产出者条目 | 1 条，200~400 字 | 1 条，400~500 字 | 1 条，400~600 字 |
| 消费者条目 | 1~2 条，每阶段一条 | 每阶段一条 | 每阶段一条，各自成篇 |
| 每轮那一行 | `阶段：序章` | `[TAG\|阶段2\|名]` | `[ARC_MAIN\|主线1\|名]` |
| 阶段内容长度 | 300~800 字 | 800~1500 字 | 1500~2500 字 |
| order 安排 | 与其余条目同段 | 单开一段 | 单开一段（ArC 用 1,090,000） |

**小卡的最小可用配置**（一个场景、一次真相揭开，就两条）：

```text
条目 1：运行·阶段契约        constant: true    ← 件 1 + 件 2
条目 2：主线·揭开             constant: false   ← 件 3，键 = 阶段行的第二态
```

**小卡最容易犯的错**：把三个阶段全写进**同一条**条目正文，用
`### 第一阶段` / `### 第二阶段` 分段，然后只挂几个情绪泛词当键
（例：`破绽` `奇怪` `不对劲`）。

**这样做的后果**：三个阶段的内容**同时**进 prompt，早期就剧透完了；
而键又是泛词，平时乱触发、真要推进时又推不动。

**正确做法**：每个阶段**各自一条**，键 = 那个阶段自己的阶段行。

## 六、常见坑

| 坑 | 症状 | 修法 |
|---|---|---|
| **只有章节、没有契约** | 键是暗号，永不触发 | 补件 1 产出者条目 |
| **契约不写"每轮"** | 第一轮有阶段行，之后没了 | 写明「每轮保留一条」 |
| **契约没列全枚举** | 后面的阶段没有对应条目 | 枚举列全 |
| **三段挤一条** | 提前剧透 + 泛词误触发 | 拆成每阶段一条 |
| **键与契约不逐字一致** | 差一个标点就断 | 逐字比对 |
| **阶段名用了文风过滤禁用词** | 存储里被删掉或改写，键永远失配 | 阶段名避开禁用词（见 §六附） |
| **阶段条目写成常驻** | 全剧透 | `constant: false` |
| **拿轮数当推进条件** | 剧情自己跑，玩家跟不上 | 改为收尾事实 |
| **阶段行排在状态块之后** | 只是显示上被面板正则吞掉，**不影响触发** | 想看见就排在状态块之前 |
| **只有大卡才做** | 小卡主线也推不动 | 小卡用小号配置，契约照写 |

## 六附、真会吃掉阶段行的东西：宿主文风过滤

`settings.styleFilterEnabled` **默认开启**（规则在 `app.js` L990-994）。
它**不在卡里**，卡作者关不掉，跑在两个会伤到令牌的位置：

- `app.js` L4902：**写回存储时**（`assistantMessage.content = filterBlockedStyleText(...)`）→ 改了就永久变了
- `app.js` L1063：**扫描窗的预处理里**（`getPostprocessedChatMessages` 内层叠了这一层）

实测（复刻源码规则）：

| 阶段行 | 文风过滤后 |
|---|---|
| `[ARC_MAIN\|主线1\|可以留在这里吗]` | ✅ 原样保留 |
| `[ARC_MAIN\|主线5\|极其漫长的一天]` | ❌ 变成「漫长的一天」→ 键失配 |
| `[ARC_MAIN\|主线1\|不容置疑的温柔]` | ❌ 整行被删 |
| `[ARC_MAIN\|主线4\|像在昨天]` | ❌ 整行被删 |

**规矩：阶段名里不要用这些词**（从源码词表抄出，非穷举）：

```text
极其 / 不容置疑 / 不易察觉 / 难以觉察 / 微不可察 / 几不可察 / 一抹 / 弧度 /
生理性 / 微微泛 / 因为用力 / 像在 / 风箱 / 手术刀 / 上扬 / 带着一种 /
语气很平 / 声音很平 / 指尖…发白 / 指节…泛白 / 像…，又像… / 不是…而是/就是…
```

**为什么这一条比"正则吞令牌"重要**：正则是**你自己写的**，有问题你看得见；
文风过滤是**宿主内置**的，改你的文本时不报错、不留痕。
阶段名一律用**叙事语言**（`天亮以前` / `回家的路` / `黑之枢机`），
天然避开这张表 —— 这也是 §二 件 2 那条「AI 能在正文里自然写出」的另一个理由。

## 七、交付自检

做完主线部分，逐条打勾：

- [ ] 这张卡真的需要阶段机？（有"后面才会发生的事"）
- [ ] 有一条 `constant: true` 的产出者条目？
- [ ] 它写全了五件事（格式 / 枚举 / 初始 / 推进 / 位置）？
- [ ] 它明写了「**每轮**保留」？
- [ ] 阶段行格式 AI 能自然写出，不是纯暗号？
- [ ] 每个阶段各有一条 `constant: false` 的消费者条目？
- [ ] 消费者键与契约枚举**逐字**相同（含转义）？
- [ ] 推进规则写的是收尾事实，不是轮数？
- [ ] 每个阶段都写了入口 / 正在发生的事 / 收尾事实？
- [ ] 阶段名的用词避开了文风过滤禁用词？
- [ ] 阶段行排在状态块之前？

## 八、和现有工具的关系

**本页是给写卡的人看的，不是机器能查的。**

RP-Hub 没有"这条卡有没有好好搭阶段机"的自动判据 ——
因为**大多数卡压根不该有阶段机**，硬查必然误伤纯日常卡与纯肉卡。

`key-audit.mjs` 会给出五档里的 **S 档**（被常驻条目点名），
但要**注意它分不清真假**：

- **真救活**：常驻条目列的是人名地名 → AI 每轮读到，聊到时**会写出来** → 条目被拉进
- **假救活**：常驻条目列的是暗号（`ST_A1`）→ AI 读到了但**不会写进正文** → 条目永远拉不进

所以看到 S 档比例高，**不等于触发没问题**。
判断办法回到本页第一节：**去产出者条目里找那句"每轮必写"**。
找得到 → 真的；找不到 → 那些键其实一条都活不了。
