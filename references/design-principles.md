# 角色卡设计原则（平台无关）

> 来源：2026-09-30 对一张第三方成品卡的完整审计。
> 本文只谈"这张卡需要什么能力"，不谈任何平台怎么实现。
> 平台实现见同目录 `platform-bindings.md`。
> **硬约束：本文不得出现任何平台名或平台专有字段名。**

## 为什么要有这一层

一张卡的设计思想与平台无关，实现手段高度依赖平台。
把两者焊在一起，换平台就等于重写规范。
因此：**规范只声明能力，平台各自提供绑定。**

## 一、三条铁律

### 1. 卡面瘦身

卡面字段只放**无法从别处推导**的东西。凡是规则、设定、写作要求，一律下沉到世界书。

反例（审计实测）：某卡卡面开场白只有 17 个字符，纯开关；写作规则全部住在常驻条目里。
正例的反面：把写作规范写进卡面 —— 卡面不进关键词扫描窗口，写了也不触发，只白烧上下文。

### 2. 单一事实源

正文契约由**世界书写定**，UI 只转录、不定义规则。
同一套规则绝不出现在两个地方。

**检查方法**：通读 UI 层，问"这里有没有一条规则，是世界书里没有的？"
有 → 规则分叉，迟早两边打架。

### 3. 状态必须落盘

任何**跨轮状态**都要有明确的"家"和恢复路径。
禁止只存内存，也禁止只靠"重扫聊天记录"重建 —— 分支切换或上下文压缩后必然丢失。

**检查方法**：为每个跨轮状态字段回答三问 ——
① 它存在哪？ ② 分支切换后还在吗？ ③ 恢复路径是什么？

## 二、能力声明清单

设计一张卡时，声明"本卡依赖 C1/C2/…"，**不要写平台名**。
每项能力在各平台的满足方式见 `platform-bindings.md`。

| 编号 | 能力 | 说明 | 缺失后果 |
|---|---|---|---|
| C1 | 状态持久化 | 跨轮、跨楼层保存结构化状态 | 关系/进度回退，玩家察觉"记忆丢失" |
| C2 | 正文标记 → UI 渲染 | 把正文里的结构化标记渲染成界面 | UI 只能空转，或退化成纯文本 |
| C3 | 富交互回传 | UI 上的操作变回一条消息送进对话 | 按钮只能看不能按 |
| C4 | 楼层级存档与恢复 | 按楼层保存/恢复状态快照 | 分支后状态错乱 |
| C5 | 条件分支渲染 | 按当前状态显示不同内容 | UI 无法随剧情变化 |
| C6 | 模板变量替换 | 正文/UI 中嵌入变量占位符 | 内容写死，无法随状态更新 |
| C7 | 递归触发 | 条目被其它条目触发，可分层 | 只能靠一级直接命中，长链设定进不了窗 |

**C7 特别注意**：各平台对递归的支持差异极大，**有平台完全不支持**。
默认按"不支持"设计（见第三节），把递归当可选加速器。

## 三、触发设计规范

1. **默认假设无递归**。一级直接命中才可靠。需要链式才出现的设定，改成常驻索引条目或写进输出契约。
2. **递归只是加速器**。只有确认目标平台支持时才用；用了要写明"本卡在无递归平台上的降级表现"。
3. **中文不要依赖词边界**。英文的 `\b` 分词对中文无效；若平台提供"整词匹配"开关，中文下必须关闭（字段见绑定矩阵）。
4. **键从场景长出来，不从内容总结出来**。先定"这条目回答玩家什么行动/处于什么阶段"，再设计键。详见 `keyword-design.md`。
5. **区分键的可靠度**：输出契约逼出来的槽位值（最高）> 常驻条目点名（中）> UI 预填按钮（低）。

## 四、正文契约设计

### 4.1 令牌成对原则

每个正文令牌必须有**产出方**和**消费方**，缺一不可。

- 产出方：世界书契约迫使正文写出的标记。
- 消费方：把它处理掉的规则（渲染成 UI，或从提示词里剔除）。

**检查方法**：列出所有令牌，逐个回答"谁产出它？谁消费它？"
审计实测：某卡有 8 个令牌**只有消费方、零产出方** —— 等于挂了 8 个永远不亮的灯。
它们无害但白占提示预算，应当删除或补齐产出。

### 4.2 令牌书写规范

- 用固定分隔符，字段顺序固定，方便解析与校验。
- 包裹标记要能被精确匹配，避免与正文自然语言混淆。
- 定义令牌的条目应是**常驻**的 —— 否则它自己都要靠关键词才触发，契约就不稳定。

### 4.3 替换文本的 `$` 转义坑

替换机制通常沿用通用的字符串替换语义，其中 `$` 有特殊含义
（`$$`→`$`、`$&`、`` $` ``、`$'`、`$1`…）。

**结论**：替换文本里若要出现**字面 `$`**，必须写成 `$$`。
反斜杠 `\$` 在多数实现里不管用。

**检查方法**：统计替换文本中的 `$`，确认每一个要么是刻意写的反向引用，要么已经双写。

## 五、反模式清单

以下每条都有审计实测出处。

1. **UI 自造规则** —— UI 里出现世界书没有的规则，形成第二事实源。规则分叉，两边迟早打架。
   *检查*：UI 层能否逐条对应到世界书条目？
2. **状态只存内存 / 只靠重扫记录** —— 分支切换或上下文压缩后丢失。
   审计实例：某卡的主线阶段没有落盘，只能重扫聊天记录重建，分支后必然猜错。
   *检查*：每个跨轮字段的三问（存在哪 / 分支后还在吗 / 怎么恢复）能否回答。
3. **令牌有消费方、无产出方** —— 永远空转，白占预算。
   审计实例：8 个令牌零产出。
   *检查*：逐个令牌问"谁产出它"。
4. **依赖单一外部域** —— 全部重资产托管在同一个域名，该域一挂全卡失效。
   审计实例：某卡唯一远端域承担了全部界面重资产。
   *检查*：列出所有外部依赖，问"挂掉一个还剩多少能用"。
5. **把阶段推进写成数值计数器** —— 若实际机制是"剧情演到某收尾节点则前进"，
   就**不要**描述成"计数到阈值自动切换"。语义失真是最贵的错误：照着错的描述去写，永远调不对。
   审计实例：某卡明写"主线不会因玩家空闲而自动播放"，实际推进靠当轮收尾事实；
   而"阈值"在该卡里只用于角色亲密度与战斗撤退。
   *检查*：机制的触发条件是"计数"还是"事件"？读一遍原始规则文本，别凭印象。

- [ ] 每个跨轮状态都能回答三问？（铁律 3）
- [ ] 已声明依赖的能力编号（C1–C7）？
- [ ] 所有令牌都有产出方和消费方？（§4.1）
- [ ] 替换文本里的字面 `$` 都已写成 `$$`？（§4.3）
- [ ] 逐条核对过第五节 5 条反模式？
- [ ] 若用了递归，写明了无递归平台上的降级表现？（§3.2）
