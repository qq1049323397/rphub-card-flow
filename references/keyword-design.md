# 关键词设计：从场景长出来，不从内容总结出来

> 来源：2026-09-23 审计用户上传的《世界书关键词审查修理》skill，取其可执行部分，
> **剔除其中与 RP-Hub 源码冲突的说法**（见 `key-reachability.md` 裁决表）。
> 本文档只保留在 RP-Hub 上验证成立、且本插件工具未覆盖的设计方法。

## 一、三段设计法（设计侧核心）

**严禁把键从条目内容里总结出来塞进 keys。** 这是最隐蔽的坏卡流水线：
逐条给每个条目配上"看起来对"的词，死键率必然是 0，但键全是泛词，问题全在误触发。

正确顺序：

1. **先定场景需求**：这条目回答玩家的什么行动 / 到访什么地点 / 处于什么阶段？
   先有场景，后有条目。没有场景需求就不该有这个条目。
2. **再查现有机制能否养活它**（见下表）。**没机制 → 先补机制再谈键。**
3. **最后设计键**：键 = AI 被契约逼着写的槽位值，或行为发生词。

### 机制优先级表（RP-Hub 口径）

| 机制 | 键怎么被养活 | 可靠度 | RP-Hub 支持 |
|---|---|---|---|
| **平台自带契约（时间戳）** | **宿主预设逼 AI 每轮输出时间**，键 = 时间片段 | **最高（不花自己的条目）** | ✅ 内置 `时间戳` 规则，可开关 |
| 输出契约（状态栏/场景头每轮必写） | 键 = 槽位值枚举（地点/时辰/阶段） | 最高（每轮必进窗） | ✅ 靠 prompt 约定 + 正则承接 |
| 常驻索引条目 | 上游正文点名下游条目名 | 中（每轮进 prompt） | ✅ `constant:true` |
| 开场白 UI 按钮 | 点击送字面 | **低**（预填，需玩家按发送） | ⚠️ `data-slash` + `triggerSlash` |
| 思维链 CoT 引导 | 常驻法则要求 AI 复述状态 | 中（靠服从性） | ✅ 写进常驻 |
| `probability` | 低频条目用概率补偿 | 辅助，不能当唯一通道 | ✅ |

**注意**：`triggerSlash` 不是"点了就触发"。它把文本存进 `pendingCardInteraction` 并聚焦输入框，
**仍需玩家按发送**（`app.js` L7723-7735）。别把它当可靠入口。

### 判据：键要挂在「有东西保证它每轮出现」的地方（2026-10-04 新增）

上一张表容易读成"选个好的键类型"。真正的判据只有一句：

> **键的可靠度，等于「有多少机制保证它每轮出现在正文里」，与它是什么词类无关。**

所以同一个键类型，在不同卡上的可靠度可以天差地别：
日期在**有输出契约的卡**上是最高档，在**没有时间要求的卡**上就是死键。

#### 平台自带契约：唯一一条白送的通道

**时间戳**值得单列，因为它是**宿主替你养的键**，不用你写任何契约条目：

- RP-Hub 内置预设带 `时间戳` 规则（`built-in-content.js`，可开关）：
  要求正文第一行单独输出「【2023年08月01日 07时】」。
- 同一份内置内容里还有一条总结规则：正文带有效时间戳时，
  必须把它用【】包裹、独占总结第一行 —— **时间戳会进总结，也进记忆**。
- 酒馆侧的预设普遍也带时间戳类要求。**进酒馆的卡基本都能吃到这一档。**

于是「日期/时间做键」在某些卡上能成立。**但要注意成立的原因**：

```text
✅ 成立：宿主逼 AI 每轮写时间 → 时间每轮进窗 → 日期键每轮可命中
❌ 不成立：因为「日期是个好键」→ 换一张没有时间要求的卡，日期键直接死
```

**这就是为什么不能把"用日期做 key"写死成规范。**
主线入口可以是日期、物品名、阶段码、地点名 —— 载体随意，
**只要那个载体有机制保证它每轮出现**。

#### 怎么判断一个键有没有被养活

问三句，任何一句答不上来，这个键就是死的：

1. **谁保证它每轮出现？**（平台预设 / 卡自己的输出契约 / 常驻索引 / 无）
2. **它出现在正文的哪个位置？**（每轮必写的那张表里 / 只在特定场景）
3. **换一张卡它还成立吗？**（成立 → 是机制；不成立 → 只是这张卡的巧合）

第 3 句最容易被跳过。**把个案的巧合写成规范，是这一页最贵的错误。**

#### 没有平台契约时，自己造一条

平台不给时间戳，就**在常驻输出契约里自己加**（RP-Hub 口径）：

- 要求 AI 每轮在正文开头写一行场景头（地点 / 时辰 / 阶段）
- 把要当键的值**枚举清楚**（§二第 4 条：契约槽位值必须逐字等于枚举）
- 用正则把这一行在显示层隐藏（`markdownOnly`），**但发出副本保留**（见 §五）

这条契约一旦立住，就等价于"自己造了一个平台自带契约"，
**键的可靠度直接进最高档**。这是小卡最划算的投资。

## 二、短键原则（部分成立，需要精确表述）

原 skill 的「非专有名词一律 ≤2 字」是一个**有用的启发式，但不是铁律**。实测：

- 键匹配是**大小写不敏感的子串匹配**（`useRegex=false`），
  正文/输入必须逐字包含键才命中。所以长键确实降低召回率。
- 但实测某张范本卡 2 字键与 3-4 字键命中率都是 99%（因为该卡键都进了常驻索引），
  说明**键长不是决定因素，键是否被机制养活才是**。
- 真正的问题在**链式依赖**：键只出现在自己条目正文里，就只可能靠上游带动。

**可执行版本**：
1. 同一概念的近义词**各拆各键**（keys 数组本身就是 OR），不要合成一个长短语。
2. `useRegex=true` 时，弹性来自**分支粒度**：
   ✅ `(?:请仙|典仪).{0,8}(?:遇刺|陨落)`
   ❌ `(?:请仙典仪帝君遇刺)`（一个长分支，等同长字面键）
3. 专有名词（人名/地名/组织/作品/功法/编号令牌）**整体保留**，拆开反而误触发
   （`希`/`尔` 会命中一切）。
4. 契约槽位枚举值**必须逐字等于**枚举，不可为凑短改写 —— 不对齐比长键更糟。

## 二附、裸名保底：键 ⊆ 裸名（v0.7.0 新增）

**上一节说的是"长键降低召回"，容易读成"键要短"。那是误读。**
真正的判据与长度无关：**键必须是条目裸名的子串**。裸名 = 该实体在正文里的自然称呼。

### 病因实录

一张 137 条的卡，23 个场所条目的键全是前缀形态：

```
场所·货运仓库 → keys: ["地点：货运仓库", "前往货运仓库", "去货运仓库", "调查货运仓库"]
```

它的常驻输出契约要求「地点槽逐字采用『地点：场所名』」，作者照着契约写键。
常驻索引条目也**照着键抄**成 `地点：货运仓库`。于是：

| 检查 | 结果 |
|---|---|
| 字面死键率 | 0.0% |
| 常驻索引覆盖 | 93.4% |
| S 档（索引点名） | 92.4% |

**全绿，但触发是死的。** 因为 AI 在正文自然写「我去了货运仓库」时：
键 `地点：货运仓库` 不是 `货运仓库` 的子串（反过来才对），子串匹配**命中不了**。

实测矩阵（文本 → 是否命中 `地点：货运仓库`）：

| 文本 | 命中 |
|---|---|
| `地点：货运仓库` | ✅ |
| `前往货运仓库` / `去货运仓库` / `调查货运仓库` | ✅ |
| `我去货运仓库看看` | ❌ |
| `我去了货运仓库` | ❌ |
| `我到了货运仓库` / `我走进货运仓库` | ❌ |
| `货运仓库里很安静` | ❌ |

契约合规面板（`去向：货运仓库；沉落图书馆`，都按契约写裸名）→ **23 个场所条目 0 条触发**。
同一轮 `地点：楼顶电台` 能触发，因为面板逐字写了那个前缀形态。

### 铁律

> **每条非常驻条目的 keys 里必须有它的裸名。判据：存在一个键 ⊆ 裸名（含相等）。**

- **长度不限。** `黑炎龙武装修罗铠甲` 就用全名，不要为凑短砍成 `铠甲`。
  `Corvin`（6 字符）与它同等通过 —— 判定不看字符数。
- **前缀形态与动作形态是额外通道**，可以留（契约槽位确实会逐字输出它们），
  但不能代替裸名。
- **索引抄键是假的自我一致。** 索引和键逐字相同，会让所有"键有没有被常驻点名"的
  检查通过，而正文仍然写不出键。

### 与「常驻索引覆盖」的分工

| 检查 | 回答的问题 | 保证什么 |
|---|---|---|
| 常驻索引覆盖 | AI **读得到**这个名字吗 | AI 知道有这个地点 |
| 裸名保底 | AI **写得出**这个名字吗 | 文本一旦写裸名，条目必触发 |

索引保证不了后半句。**两个都要做，不互相顶替。**

### 别称：长专名的必然产物

`黑炎龙武装修罗铠甲` 在正文里会被自然简称（`修罗铠甲`）。只挂全名 → 正文写简称 →
条目饿死。所以 **原创卡要主动定别称，把别称也放进 keys**。

**别称的唯一红线：必须是专名。** `修罗铠甲` 可以，`铠甲` 不行 —— 后者是泛词，
会命中一切铠甲（见第三节"泛词键"）。

### 命名期：先定裸名，再写条目

在「读骨架」之后、「选一段开写」之前，先决定每个条目在正文里叫什么：

- **无素材（一键出卡）**：AI 自己命名时当场登记裸名，边命名边记。
- **有素材（docx / 聊天记录 / 既有设定）**：AI 读入挑出专名，产出候选清单 + 别称，
  作者确认后才写条目。

### 为什么不做专名抽取算法

实测同一份样例（含「藤本秋」7 次、「黑炎龙武装修罗铠甲」2 次、「周迟」2 次）：

| 阈值 | 抽出 | 问题 |
|---|---|---|
| ≥3 次 | 藤本秋 | 精准，但漏掉只出现 2 次的两个专名 |
| ≥2 次 | 藤本秋、周迟、`黑炎龙武装修罗铠`、`炎龙武装修罗铠甲`、东西 | 真名进了但**边界全错**，还混进泛词「东西」 |

阈值法没有语义：降阈值抓全就进噪音，升阈值精准就漏名，中间没有甜蜜点。
**这一步交给 AI 阅读理解 + 作者确认，写成脚本只会给出边界错误的假答案。**

### 怎么检查

```bash
node gate.mjs "<卡>"                    # 「裸名保底」项，不过 = exit 1
node key-audit.mjs "<卡>" --list-bare   # 列出每条缺裸名的条目与该补的键
```

裸名来源：`content` 开头的 `<标签>` 优先（作者自己声明的实体名，最准）；
退回 `comment` 的第二段（三段式只取中间段）。都取不到标「裸名未知」，**不报错** ——
宁可不查，也不用切错的裸名报假问题。

豁免只有两类：`constant` 条目；正则键匹配到常驻枚举值。**不按"是不是正则"豁免**，
否则会漏放 `装备X` 这类没人养的键。

## 三、误触发：比死键更隐蔽的病

死键看得见（键哪都不出现），误触发看不见（键哪都出现）。

| 病灶 | 症状 | 处方 |
|---|---|---|
| 泛词键 | `擦过`/`额头`/`闷哼` 这类跨场景词，玩家写"发烧额头烫"也拉进官能条目 | 换**行为发生词**短键 + 挂 `probability` |
| 键 = 状态栏槽位值 | 每轮必写的枚举值全成了键 → 该组条目**每轮全进** | 检查密度；槽位值键只给"每轮都该在场"的条目 |
| 人名键拉官能内容 | 人名一出现官能条目必进，无论场景是否色情 | 改动作词键或挂概率 |
| 键覆盖全卡 | 见"照着内容生成"流水线 | 重做三段设计 |

**密度基准**：单轮平均拉取 5-6 条健康，7-8 可接受，10+ 过高，30+ 病态。

自检方法：写 3-10 组该卡实际玩法的模拟正文（含卡自己的状态栏/锚点格式），
跑字面匹配，数单轮拉取条目数并定位误触发。

## 四、必须核的三件事（交付前）

1. **契约-键名对齐**：输出契约要求的枚举词，与条目键是否**逐字相同**？
   两套命名（UI 变量「序章/博弈交锋」vs 条目键「第二阶段/第三次博弈」）= 键白设。
2. **阶段名避开宿主文风过滤词**：这不是卡内正则的问题 —— 卡里的美化/隐藏正则
   **只作用于渲染那一份，从不写回存储**（详见 `mainline-trigger.md` §六附）。
   真正会在**存储层**改写令牌的是宿主内置的文风过滤（`styleFilterEnabled` 默认开，
   `app.js` L4902/L1063）：阶段名里出现 `极其` `一抹` `像在` `不容置疑` 这类词，
   会被删掉或改写 → 键永远失配。**阶段名用叙事语言，天然避开。**
3. **时机限定写在正文里**：阶段条目正文没写"仅当第 X 阶段生效" → 早期就剧透后期内容。
4. **裸名入键（v0.7.0）**：每条非常驻条目有没有一个键 ⊆ 它的裸名？
   跑 `node key-audit.mjs "<卡>" --list-bare`，清单必须为空。见第二附节。

## 五、RP-Hub 没有递归，但也没有条数上限（2026-09-30 新增）

**这一条最容易被外来的写法误导，也是"主线推不动"的根因之一。**

先纠正一个流行说法：有资料写"当前宿主单次选择"（一轮只挑一条）。
**这是错的。** 源码事实（`data-services.js` L581-636）：

- 非 `constant` 条目逐个检查 keys 是否命中扫描窗；
- **凡命中者一律写进 `triggerMap`，没有条数上限**；
- 之后按 `order` 排序**全量注入**。

`injectContextMessages` 里的 `safeTargetLimit`（L747/L765）是
**插入位置的下限**（`splice` 的落点），**不是配额**。别被名字骗了。

### 于是正确的设计姿势是「同轮全命中」，不是「链式唤醒」

| | 有递归的平台 | RP-Hub |
|---|---|---|
| 一条命中后唤醒另一条 | ✅ 支持 | ❌ **不支持** |
| 一轮能进几条 | 受预算限制 | ✅ **无上限，命中即全进** |
| 结论 | 可以链式铺开，靠上游带下游 | **必须让同一场景要用的条目各自命中** |
| 反面 | — | 指望"A 条目触发后 B 跟着来" —— 永远不会发生 |

**所以**：同一场景该同时在场的东西（地点 + 在场人物 + 当前阶段 + 相关事件），
**把各自的键都挂上，让它们同轮一起命中**。

这也是为什么「常驻索引条目」是无递归平台的主要解药 ——
它把名字摆在 AI 眼前，让下游条目的键**能被写进正文**，从而**自己**命中。

> 注意：**能被写进正文的才叫救活。**
> 常驻条目里列人名地名 ✅；列 `ST_A1` 这种暗号 ❌ —— AI 读到也不会写。
> 详解见 `mainline-trigger.md` §八。

### 常见误用

| 误用 | 为什么错 | 改法 |
|---|---|---|
| 设计成"A 触发后 B 才来" | 宿主无递归 | B 也挂上自己该有的键 |
| 怕"进太多"而故意少挂键 | 宿主无上限，命中就进；少挂只是让它进不来 | 该挂就挂，靠**键的精确度**控密度，不靠少挂 |
| 把 `safeTargetLimit` 当配额 | 它是插入位置下限 | 忽略它，按 `depth` 语义理解 |

**控密度靠键的准确度，不靠省键。** 密度基准见本文第三节。

## 六、与 `key-reachability.md` 的分工

- 本文档：**怎么设计键**（设计侧方法论）。
- `key-reachability.md`：**键能不能被触发**（运行时事实 + 五档分档 + 源码证据）。
- `mainline-trigger.md`：**主线/阶段机怎么搭**（产出者-消费者往返）。
- 工具：`key-audit.mjs` 打分档（诊断），`gate.mjs` 过闸门（守门）。
